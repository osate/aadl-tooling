# SOM Reachability Analysis Description

This describes what the OSATE mode (System Operation Mode) reachability analysis
(`org.osate.analysis.modes.reachability.ReachabilityAnalyzer`) produces. It is a
sibling of [flow-latency-output.md](flow-latency-output.md) and
[bus-load-output.md](bus-load-output.md), and is intended as a reference for the
`aadl.analyze.reachability` language-server command.

The analysis and its algorithm are documented in the SEI report *Reachability of
System Operation Modes in AADL* (the LaTeX source lives at
`~/git/aadl-modes/report/`). The conceptual summary below is drawn from that
report; the output-structure sections are drawn from the current Java
implementation in `org.osate.analysis.modes`.

## Concept: what is computed

Each AADL component can have **modes** (a configuration: which subcomponents and
connections are active, plus mode-specific property values). One mode is the
*initial* mode. A component transitions between modes in response to an event
received on a port, generated internally, or generated by a subcomponent.

> "The set of all component modes in an AADL instance model is called the
> *system operation mode* (SOM). The initial SOM is defined as the model
> components' set of initial modes."

The *possible* SOMs are all combinations of component modes; in general some are
not **reachable**. The analysis constructs:

- the set of **reachable SOMs** (those reachable from the initial SOM by a
  sequence of SOM transitions), and
- the **SOM transitions** between them, each labeled with the trigger event.

A possible SOM is *unreachable* when, e.g., a trigger event's source component or
connection is inactive, a trigger is not connected to an event source, or a
component mode is not reachable from its initial mode. Mode transitions triggered
by the **same event happen simultaneously** (AADL standard rule), which the
algorithm enforces; for modal connections it tracks which **trigger connections**
must be active for a transition to be enabled.

### Algorithm shape (for context)

- Process component instances in **pre-order** (parent before subcomponents),
  starting from the always-active root system instance.
- Incrementally extend the SOM set with each component's mode states and **merge**
  its mode transitions into the SOM transitions, then **drop SOMs unreachable**
  from the initial SOM after each component.
- A component's *mode state* is one of `⊤` / `⊤ₘ` (active, optionally in mode m)
  or `⊥` / `⊥ₘ` (inactive, optionally resuming in mode m). Reactivation uses
  `Thread_Properties::Resumption_Policy` (`restart` → initial mode, `resume` →
  last mode); the implementation defaults to `restart` when unset.
- For modal connections, transitions carry the set of trigger connections that
  must be active; at the end, **dominated transitions** (those whose required
  connection set is a strict subset of another's between the same SOMs) are
  removed.

The implementation generalizes this with **mode domains** (`SEI::Mode_Domain`):
the model can contain several independent mode domains, each analyzed separately
(a domain may not be nested inside another, and a modal component must be inside
a domain — both are validated). The whole-system SOMs are the combinations of
per-domain SOMs.

## Three forms of output

A command run produces output in three forms:

1. An in-memory `AnalysisResult` object (the structured model).
2. Optional report files, written only for the formats enabled in the
   `ReachabilityConfiguration` (DOT, HTML, SMV — see §2). An EMF `.modemodel`
   resource holding the SOM graphs is also created next to the instance model.
3. The text string returned by the LSP `aadl.analyze.reachability` command.

### 1. The `AnalysisResult` structure

Built by `ReachabilityAnalyzer.analyzeModel()`:

```
AnalysisResult
  analysis     = "SOM Reachability Analysis"
  modelElement = the analyzed SystemInstance
  resultType   = SUCCESS | ERROR | FAILURE | TBD (see below)
  message      = "" on success, else an explanatory message (see resultType)
  diagnostics  = info: "<som-name> is not reachable" — one per unreachable
                 instance-model SOM;
                 validation errors: "Modal component not in a mode domain",
                 "Mode domain contained in another: <qualified-name>";
                 report-file write/delete failures (see §2)
  results      = one Result per analyzed mode domain,
                 plus one Result per written report file (see §2)
```

`resultType` / `message` are set from the per-domain results:

- `FAILURE` — "The analysis could not be executed successfully"
- `ERROR` — "An error occurred during analysis, check instance model for problems"
  (also set immediately, with message "Mode domains are not set up correctly,
  check instance model for problems", if mode-domain validation fails)
- `TBD` — "Analysis was cancelled"
- `SUCCESS` — message left empty

Each **per-mode-domain `Result`** (from `ModeDomainAnalyzer.analyze`):

```
Result
  modelElement = the mode-domain root ComponentInstance
  message      = "SOM Reachability Analysis"
  resultType   = SUCCESS | TBD (canceled) | FAILURE
  diagnostics  = info "canceled" if the domain analysis was canceled
  values       = (none)
```

The detailed reachable-SOM / transition data is **not** stored as nested
`Result` values; it lives in the SOM graph model (`SOMGraph` levels of
`SOMNode`s with transitions) that backs the exporters. The `AnalysisResult`
captures the domain-level outcome and the unreachable-SOM diagnostics; the
graphs carry the full reachable-SOM set and transitions.

#### Unreachable-SOM diagnostics

After analysis, `markUnreachableSOMs()` walks the instance model's SOMs
(`SystemInstance.getSystemOperationModes()`) and matches each against the
reachable nodes in the SOM graphs. Every instance-model SOM that does not match a
reachable path produces an **info** diagnostic: `"<som-name> is not reachable"`,
attached to that `SystemOperationMode`. (Reachable SOMs produce no diagnostic.)

### 2. Files written to disk

File generation is controlled by `ReachabilityConfiguration` flags
(`withDot()`, `withHTML()`, `withSMV()`, `withModel()`); by default **all are
off**. `writeReports()` writes each enabled format and, for each disabled format,
**deletes** any stale file of that type. All files are written via EMF
`URIConverter`, next to the SOM-graph resource at:

```
<instance-dir>/reports/som-reachability/<rootname>.<ext>
```

where `<ext>` is `dot`, `html`, or `smv` (the backing graph resource itself uses
`.modemodel`). For each file successfully written, a `Result` is appended to the
`AnalysisResult`:

```
Result
  message   = "DOT file URI" | "HTML file URI" | "SMV file URI"
  values[0] = (String) the written file's URI
```

The three formats:

- **DOT** (`DotExporter`) — a Graphviz `digraph` (`rankdir=LR`). One subgraph per
  mode domain (labeled `Mode domain D<n>: <domain-root-path>`), with a nested
  cluster per component level. Each SOM-graph node is rendered with label `⊤` /
  `⊥` plus `[mode]` if it has one; the initial node is `filled`, derived modes
  `dashed`. Red edges (`arrowhead=none`) link the mode-state tree; unreachable
  links are `dashed`. Grey edges between leaf nodes are the SOM transitions,
  labeled with the trigger feature's instance path. Dead (fully unreachable)
  subtrees are pruned.

- **HTML** (`HtmlExporter`) — a self-contained page titled "System Operation
  Modes and Transitions for \<root>". Per mode domain it shows an **SOMs table**
  (rows = SOMs `som0, som1, …`, columns = components; a cell shows the
  component's mode in that SOM, empty if the component is inactive) and a
  **transition table**. Notes explain the table and that these `somN` names are
  unrelated to the instance model's SOM names.

- **SMV** (`SmvExporter`) — NuSMV input. One `MODULE D<n>` per mode domain with
  an `IVAR trg` (trigger), a `VAR som` state variable, `init(som)` and
  `next(som) := case … esac` transition relation, and a `VAR c<i>` per modal
  component giving its mode per SOM. A `MODULE main` instantiates one variable
  per domain. Users can add LTL/CTL formulae and check them with NuSMV. (If a
  domain has no modal components or no SOM transitions, a short explanatory
  string is emitted instead.)

### 3. LSP command return value (`aadl.analyze.reachability`)

The command returns a single newline-separated string:

```
Ran mode reachability analysis of <instance-uri>
<absolute path to each written report file, one per line>
<gcc-style diagnostic line>
...
```

with each diagnostic line collected from the `AnalysisResult` diagnostics
(including the "\<som> is not reachable" infos and any validation errors) and
sorted, in the same form latency/bus-load use:

```
<instance-file-path>:<element-instance-path>: <severity>: <message>
```

The command takes the instance `.aaxl2` URI and optional booleans selecting which
report formats to generate (DOT / HTML / SMV), mapping to the
`ReachabilityConfiguration` `with*()` options. Omitted booleans default to off.

The `osate-cli` `analyze-modes` subcommand and the VSCode
`aadl2.analyze.reachability` command both forward to this command and display/print
the returned string.
